### 로컬 파일 구조 조사에서 나온 사실 ([tools/survey.py](../tools/survey.py), 읽기 전용) **[확인]**

1. **확장자와 실제 형식이 다를 수 있음.** 확장자가 `.hwp`인 문서 2개가 내용은 실제로 HWPX(ZIP)임. → 형식은 반드시 **매직 바이트로 판별**해야 함.
2. **HOP/rhwp로 저장한 것으로 보이는 HWP 2개에 비표준 스트림 `RhwpHwpxOrigin`이 들어 있음.** (2026-08-11, 2026-10-25에 저장된 개인 문서 2개). 같은 이름의 HWPX 원본도 있어서 **HWPX→HWP 변환 저장**으로 추정됨 **[가정]**. 한컴이 이 스트림을 어떻게 처리하는지는 **미검증**.
3. 한컴이 만든 HWP에는 `FileHeader, DocInfo, BodyText/Section*, BinData/*, HwpSummaryInformation, PrvText, PrvImage, DefaultJScript, JScriptVersion, _LinkDoc` 스트림이 공통으로 들어 있음. HWPX에는 `mimetype`(첫 항목, 무압축), `version.xml, settings.xml, META-INF/{container.xml, container.rdf, manifest.xml}, Contents/{content.hpf, header.xml, section0.xml}, Preview/*`, 그리고 일부 파일에 `Scripts/*`, `Chart/*.xml`이 있음. → **편집기가 다루지 않는 스트림/항목도 바이트 그대로 보존**해야 함.
4. 대용량 파일(12MB, 115MB)은 간이 CFB 파서가 처리하지 못함(DIFAT 확장 미구현). 실제 파서에서는 대용량 및 300MB급 이미지 포함 문서를 성능 테스트 대상으로 둬야 함.
5. macOS `._*` 파일(AppleDouble)이 `.hwp` 확장자를 달고 섞여 있음 → 열기 단계에서 명확한 오류를 내야 함.

## 3. 명세와 라이브러리

### 명세 **[출처]**
- **HWP 5.0**: 한컴이 공개(HWP 5.0, 3.0/HWPML, 배포용 문서, 수식, 차트 문서). CFB 컨테이너 + zlib(raw deflate) 압축 레코드 스트림 구조.
- **라이선스 조건**: 자유롭게 사용 가능. 단, 결과물의 UI·매뉴얼·도움말·소스에 **"본 제품은 한컴의 HWP 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다."** 문구를 표기해야 함. 한컴은 정확성을 보증하지 않음.
- **HWPX**: KS X 6101(OWPML), ZIP+XML 구조. 한글 2021-04 패치 이후 기본 저장 형식. 표준 원문(KS 열람)은 아직 직접 확인하지 못함.

### 라이브러리 후보

| 이름 | 언어/라이선스 | 읽기 | 쓰기 | 판단 |
|---|---|---|---|---|
| **rhwp** (edwardkim) v0.8.7 | Rust, **MIT** | HWP5, HWPX, HML, HWP3 | HWP, HWPX, HML. `content_loss` 손실 보고서, raw passthrough 구조 있음(소스 확인) | **1순위 기반 엔진.** 테스트 3,400개 이상, 렌더 diff CI **[출처]**. 실제 라운드트립 품질은 **미측정** |

## 4. 한컴독스 검증 방법

- `hancomdocs.com` 접속 시 한컴 계정 로그인 페이지로 이동함 **[확인]**. 공개 API는 찾지 못함 → **CI 자동화는 불가로 간주**.
- **실현 가능한 방식(반자동)**: 앱 내장 브라우저에서 **사용자가 직접 로그인** → 테스트 파일 업로드(파일마다 승인) → 페이지별 스크린샷 → 한컴독스에서 재저장한 파일 다운로드 → 로컬 diff 도구로 비교.
- 제약: 계정 생성·로그인은 사용자가 해야 함. 외부 서버 업로드가 필요하므로 **개인 문서는 쓰지 않고 직접 만든 테스트 파일만 사용**. 무료 플랜 한도(2GB, 파일 크기 제한)는 공식 확인이 필요함.
- 보조 오라클 후보 **[가정]**: 설치된 winboat/VirtualBox에 Windows와 한컴오피스 뷰어(무료) 또는 한글을 설치하는 방법. 한글이 있으면 HwpCtrl 자동화로 열기 성공 여부와 PDF 출력을 자동화할 수 있음. 라이선스와 설치 가능 여부는 확인이 필요함.
- 테스트 원본 제작 문제: 한컴 없이는 "한컴이 만든 원본"을 확보하기 어려움 → **한컴독스에서 기능별 테스트 문서를 직접 만들어 다운로드**하는 방법이 가장 확실함.

## 5. 파일 손상 위험과 기술적 제약

| 위험 | 원인 | 대응 원칙 |
|---|---|---|
| 편집 없이 저장해도 파일이 바뀜 | 전체 재직렬화 | **변경이 없으면 원본 바이트를 그대로 복사**. 저장 버튼 비활성화 |
| 손대지 않은 부분의 손실 | 모델이 모르는 레코드/XML 노드를 버림 | HWP: 미지원 레코드/태그는 원 바이트로 보관. HWPX: 미지원 XML 노드와 속성은 원문 유지. **수정된 스트림/항목만 다시 씀** |
| 형식이 조용히 바뀜 | HWPX→HWP 저장 (HOP에서 실제로 관찰) | 원래 형식으로 저장하는 것이 기본. 형식 변환은 "다른 이름으로 저장"에서만, 경고와 함께 |
| HWP 내부 일관성 깨짐 | DocInfo ID 매핑 개수, 문단 글자모양 위치 배열, 컨트롤 문자 8 WCHAR 크기, LINE_SEG 캐시 | 편집한 문단만 다시 계산. 저장 후 **재파싱 검증을 통과해야** 원본을 교체 |
| CFB 쓰기 오류 | 섹터/미니스트림/DIFAT 할당 | rhwp `cfb_writer`를 쓰고 독립 리더(olefile 등)로 교차 검증 |
| HWPX ZIP 규칙 위반 | `mimetype`이 첫 항목·무압축이어야 함, manifest 정합성 | 수정하지 않은 항목은 압축 바이트를 그대로 복사, 순서 유지 |
| 저장 중 장애로 원본 손실 | 덮어쓰기 중 충돌 | 임시 파일 → fsync → 원자적 rename. 첫 저장 시 원본 백업(`~/.local/share/<app>/backups`) |
| 열 수 없는 문서 | 암호화, 배포용 문서, DRM | 읽기 전용 또는 열기 거부 + 명시적 안내 |
| 미리보기 불일치 | PrvText/PrvImage가 옛 내용으로 남음 | PrvText는 다시 생성, PrvImage는 보존 또는 다시 생성. 한컴 동작 확인 필요 |
| 렌더링 차이(파일 손상 아님) | 함초롬/HY 글꼴 없음, 조판 엔진 차이 | 파일 무결성과 화면 재현을 **분리해서 평가**. 대체 글꼴 매핑을 기록 |
| Linux 입력 | Wayland/IBus/fcitx 한글 IME | 네이티브 툴킷 IME 경로를 별도로 테스트 |

## 6. 아키텍처 방향 (제안, 확정 아님)

- **엔진**: rhwp(MIT) 코어 사용(파서, 모델, 직렬화). 우리 계층은 그 위에 **무결성 계층**(dirty 추적, 부분 저장, 백업, 저장 전 재파싱 검증, 손실 보고)으로 둠. 엔진을 처음부터 다시 쓰는 것은 비용 대비 근거가 없음.
- **분리**: `core`(rhwp 래핑 + 무결성) / `verify`(CLI: inspect·roundtrip·diff·render) / `ui`. PoC 단계에서 UI는 없음.
- **UI 후보** (PoC 이후 결정):
  - A) GTK4/libadwaita + rhwp 네이티브(Skia) 렌더 → 진짜 네이티브, 작업량 큼
  - B) Tauri/WebKitGTK + rhwp-studio 계열 → 빠르지만 HOP과 거의 같음
  - 현재는 A 쪽으로 기울어 있음. GTK4 개발 패키지 설치가 필요함.

## 7. 최소 PoC (UI 없음, CLI)

1. `inspect` — 매직 판별, 스트림/항목 목록, 기능 사용 현황(컨트롤 ID, 미지원 태그 목록)
2. `save --noop` — 편집이 없으면 **원본과 바이트 동일**(SHA-256 일치)
3. `edit-text` — 문단 하나의 텍스트 교체 후 저장
4. `verify` — (a) 재파싱 성공 (b) 수정한 Section/section XML 외의 스트림/항목이 바이트 동일 (c) 레코드/XML 트리 diff에서 변경이 대상 문단으로 한정 (d) 독립 파서(pyhwp/olefile/zipfile)로 교차 확인 (e) 원본과 결과의 페이지별 렌더 픽셀 diff
5. 결과는 JSON으로 저장 → 회귀 테스트 기준선

**PoC 합격 기준**: 2번 100% 바이트 동일 / 4(b) 100% / 4(c) 의도하지 않은 변경 0건 / 한컴독스에서 열기 성공 및 육안상 레이아웃 차이 0건(수동 기록).

## 8. 테스트 계획

- **코퍼스**: 지정된 9개 범주(단순 텍스트, 글꼴·문단, 표·셀 병합, 이미지·도형, 머리말·꼬리말·쪽 번호, 각주·미주, 수식·글머리표, 다단·구역·쪽 나누기, 복합). 범주마다 HWP와 HWPX 1쌍씩, 한컴독스에서 직접 작성. 별도로 로컬 실제 문서는 **로컬 전용 회귀 테스트**(업로드 금지)에 사용.
- **절차**(파일마다): 원본 열기 → 편집 없이 저장 → 텍스트 수정 후 저장 → 재열기 → 한컴독스에서 열기/스크린샷 → 한컴독스 재저장본 다운로드 → 원본·결과·한컴 재저장본 3자 비교 → `results/<file>.json` + 손실 기록표
- **자동화 범위**: 1–4단계와 6단계는 `cargo test` + CLI로 자동화. 5단계(한컴독스)는 반자동(브라우저 + 사용자 로그인).
